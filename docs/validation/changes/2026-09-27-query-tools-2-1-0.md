# Recorded change: `query-tools` 2.1.0 and an iterative `canonicalJson`, 2026-09-27

_Follows the procedure in `docs/validation/README.md`, "Change control for shared, evidenced
libraries" (steps 0–8). Audit batch B03 of the 2026-09-27 repository audit._

**What changed.** `QUERY_TOOLS_VERSION` moved from `2.0.1` to `2.1.0`, a minor under ADR 0002:

- `ProductSummary.identifiers[].value` accepts `/` (`^[A-Za-z0-9._:/-]{1,128}$`, was
  `^[A-Za-z0-9._:-]{1,128}$`). Every value valid under 2.0.1 is valid under 2.1.0.
- `QueryAuditRecord` gains an optional `degraded` (`arguments-unhashable` | `record-rejected`),
  present only on a fallback record.
- `QueryError` gains a description: a failed call is `isError: true` with one text content item
  that is exactly the code, and no `structuredContent`. The service stopped sending the error
  shape as `structuredContent`; the shape itself is unchanged.

Separately, `canonicalJson` in `src/lib/hash.ts` walks its value over an explicit stack instead
of recursing. Its output is unchanged for every input the recursive form accepted (including a
sparse array's holes); only the depth it can reach changed.

**Why.** The audit found that `find_product` would silently drop every real EMA label — its
`MedicinalProductDefinition` identifier is the EMA ePI id (`EPI/23/1047`), which the 2.0.x
grammar refused, and one refused identifier refused the whole summary — while answering
`truncated: false`. It found that arguments nested about 3,000 deep (a 6 KB body) threw
`RangeError` out of `canonicalJson` before the audit record was written, so the call left no
record and the caller received the internal error text. And it found that every tool error broke
its tool's `outputSchema` for a client that had called `listTools`, because the error shape was
sent as `structuredContent`. ADR 0002 names additive optional fields as minor and says nothing
of widening an output grammar; it is treated as minor here because no 2.0.1 value becomes
invalid and the one consumer (the agent) re-vendors in the same change.

**Impact assessment (step 0).** `src/contracts/query-tools.ts` is imported by the query service
and the contract generator; the Python agent reads the generated schema through its vendored
copy, validates success results only, and reads any `isError` result as unavailable whatever it
carries, so neither the error-delivery change nor `degraded` alters its behaviour; it now
accepts a `/` in an identifier, as the service now sends one. Zone A does not read this
contract. `src/lib/hash.ts` is imported throughout `src/` (every hash in every artefact), and
Zone A's Python port is untouched: no hash moves, which a 200,000-value differential run of the
recursive and iterative forms (zero mismatches) and the unchanged golden vectors show.
Previously produced evidence remains reproducible: no approved hash, vector or fixture moved.
Audit records written under 2.0.1 remain as written; a 2.0.1 `find_product` answer over a
document with a `/` identifier omitted that product, and no such document was in any store.

**Steps 1–6.** 1: `QUERY_TOOLS_VERSION` is `2.1.0`. 2: `contracts/generated/query-tools.schema.json`
and `contracts/generated/index.json` regenerated; `agent/scripts/sync_contract.py` rewrote the
vendored copy (`--check` passes); `agent/tests/test_contract.py` pins `/2.1.0/`. `npm run
contracts:check` shows no other generated artefact moved. 3: no fidelity vector changed. 4: the
adversarial cases are in `test/query/failure-paths.test.ts`, `test/query/acceptance.test.ts`
("find_product finds a product whose identifier is an EMA ePI id", "find_product counts a
document it could not summarise as unsearched") and `test/hash.test.ts` ("writes a value nested
far deeper than the call stack would allow a recursive walk"); each fails against the code
before this change. 5: ADR 0002 is unchanged (see "Why" for the reading of its minor rule). 6:
the rows whose evidence changed are UR-23, UR-24, UR-31, UR-42 and UR-43; their text is left
to the documentation batch that owns `docs/validation/README.md`.

**Step 7.** Not applicable: no approved hash moves.

**Blast radius.** A client that called `listTools` now receives a tool error as a tool error
(before, the SDK's client raised its own validation `McpError`). A client that read
`structuredContent` of an error result gets none; the code is the result's text. The service
now answers `400` to a body outside the ingress gate's structural bounds (`src/lib/json-shape.ts`:
nested more than 48 deep, or more than 200,000 JSON values), which no MCP message needs. The
existing `test/json-shape.test.ts` case that pinned `sha256` throwing `RangeError` at depth
20,000 now pins that it hashes; the shape bound itself is unchanged.

**Approval (step 8).** Not obtained at the time of writing: recorded in the pull request.
