# Recorded change: `query-tools` 3.0.0 and an iterative `canonicalJson`, 2026-09-27

_Follows the procedure in `docs/validation/README.md`, "Change control for shared, evidenced
libraries" (steps 0–8). Audit batch B03 of the 2026-09-27 repository audit, with its first
review round's findings closed._

**What changed.** `QUERY_TOOLS_VERSION` moved from `2.0.1` to `3.0.0`, a **major** under ADR 0002,
with a new `$id` (`https://khs.dev/contracts/query-tools/3.0.0/schema.json`):

- `ProductSummary.identifiers[].value` accepts `/` (`^[A-Za-z0-9._:/-]{1,128}$`, was
  `^[A-Za-z0-9._:-]{1,128}$`).
- A tool error is delivered as `isError: true` with one text content item that is exactly the
  closed code, and no `structuredContent` (2.0.x sent the `QueryError` shape there). `QueryError`
  carries a description saying so; its shape is unchanged.
- `QueryAuditRecord` gains an optional `degraded` (`arguments-unhashable` | `record-rejected`),
  present only when a record could not be written in full.

Separately, `canonicalJson` in `src/lib/hash.ts` walks its value over an explicit stack instead
of recursing. Its output is unchanged for every input the recursive form accepted (including a
sparse array's holes); it now reaches any depth, and refuses a value that contains itself with a
`TypeError` (the recursive form met one as a `RangeError`; an iterative walk that did not track
the containers it was inside would have looped until memory ran out).

**Classification.** ADR 0002, "Versioning": "Patch changes alter descriptions only; minor
changes add optional fields …; anything else is a new major `$id`." `degraded` alone would be a
minor. The widened identifier grammar is not an added optional field: a consumer validating
against 2.0.x refuses a 3.0.0 answer carrying an EMA ePI id. Nor is the changed error delivery:
a consumer reading an error's `structuredContent` finds none. Either makes this a major. A first
draft of this record called it a minor on the ground that every 2.0.1 value stays valid; that
reads the rule from the producer's side only, and the review of 2026-09-27 corrected it.

**Why.** The audit found that `find_product` would silently drop every real EMA label — its
`MedicinalProductDefinition` identifier is the EMA ePI id (`EPI/23/1047`), which the 2.0.x
grammar refused, and one refused identifier refused the whole summary — while answering
`truncated: false`. It found that arguments nested about 3,000 deep (a 6 KB body) threw
`RangeError` out of `canonicalJson` before the audit record was written, so the call left no
record and the caller received the internal error text. And it found that every tool error broke
its tool's `outputSchema` for a client that had called `listTools`, because the error shape was
sent as `structuredContent`.

**Impact assessment (step 0).**

- `src/contracts/query-tools.ts` is imported by the query service and the contract generator.
- The Python agent reads the generated schema through its vendored copy. It validates success
  results only and reads any `isError` result as unavailable whatever it carries, so neither the
  error-delivery change nor `degraded` alters its behaviour. It now accepts a `/` in an
  identifier, as the service now sends one. It is re-vendored and its pin moved to `/3.0.0/` in
  this change.
- Zone A does not read this contract.
- `src/lib/hash.ts` is imported throughout `src/` (every hash in every artefact). No hash moves:
  a 200,000-value differential run of the recursive and iterative forms found zero mismatches,
  and the golden vectors are unchanged. Zone A's Python port (`zone-a/src/zone_a/canonical_json.py`)
  is untouched and still recursive, so above about 1,000 levels of nesting the TypeScript form
  hashes a value the Python form raises `RecursionError` on. No artefact either side hashes can
  reach that depth: every untrusted document is refused past depth 48 by the ingress gate
  (`src/lib/json-shape.ts`) and, from this change, every query-service request body by the same
  bound. This is informational and is not a divergence on any input either side accepts.
- Previously produced evidence remains reproducible: no approved hash, vector or fixture moved.
  Audit records written under 2.0.1 remain as written. A 2.0.1 `find_product` answer over a
  document with a `/` identifier omitted that product; no such document was in any store.

**Deploy order.** A 2.0.x consumer refuses a 3.0.0 `find_product` answer that carries a `/`
identifier, so the agent must be redeployed with the 3.0.0 vendored schema **together with, or
before**, the query service's rollout of this change. Until then the deployed agent would read
such an answer as unavailable (fail closed, not wrong). The deployed agent is not yet in live
use (audit item AG-1), so the practical risk of the gap is nil; the order is stated so that it
holds when it matters.

**Steps 1–6.** 1: `QUERY_TOOLS_VERSION` is `3.0.0`. 2: `contracts/generated/query-tools.schema.json`
and `contracts/generated/index.json` regenerated; `agent/scripts/sync_contract.py` rewrote the
vendored copy (`--check` passes); `agent/tests/test_contract.py` pins `/3.0.0/`. `npm run
contracts:check` shows no other generated artefact moved. 3: no fidelity vector changed. 4: the
adversarial cases are in `test/query/failure-paths.test.ts`, `test/query/acceptance.test.ts`
("find_product finds a product whose identifier is an EMA ePI id", "find_product counts a
document it could not summarise as unsearched") and `test/hash.test.ts` ("writes a value nested
far deeper than the call stack would allow a recursive walk", "refuses a value that contains
itself, and writes one reached twice"); each fails against the code before this change. 5: ADR
0002 is unchanged; this change follows its major rule. 6: the rows whose evidence changed are
UR-23, UR-24, UR-31, UR-40, UR-42 and UR-43; their text is left to the documentation batch that
owns `docs/validation/README.md`.

**Step 7.** Not applicable: no approved hash moves.

**Blast radius.**

- A client that called `listTools` now receives a tool error as a tool error (before, the SDK's
  client raised its own validation `McpError`). A client that read `structuredContent` of an
  error result gets none; the code is the result's text.
- An answer whose own audit record cannot be written is now `unavailable` rather than the
  content, so the record the HTTP layer writes matches what the caller got.
- The service now answers `400` to a body outside the ingress gate's structural bounds (nested
  more than 48 deep, or more than 200,000 JSON values), which no MCP message needs.
- The existing `test/json-shape.test.ts` case that pinned `sha256` throwing `RangeError` at depth
  20,000 now pins that it hashes; the shape bound itself is unchanged.

**Approval (step 8).** Not obtained at the time of writing: recorded in the pull request.
