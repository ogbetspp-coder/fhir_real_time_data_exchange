# Recorded change: Node runtime `node:22.14.0` → `node:22.22.0`, 2026-09-22

_Moved verbatim from `docs/validation/README.md`, whose "Change control for shared, evidenced
libraries" section holds the procedure (steps 0–8) this record follows. The UR- rows and
section names it cites ("above", "Release criteria") are in that file.
"The previous record" and "the record above" mean [`query-tools` 2.0.1 and the `src/fidelity/index.ts` re-export, 2026-09-22](2026-09-22-query-tools-2-0-1.md)._

**What changed.** The runtime ADR 0003 pins moved from `node:22.14.0` (ICU 76.1, Unicode 16.0)
to `node:22.22.0` (ICU 77.1, Unicode 16.0): both stages of `Dockerfile` and `Dockerfile.query`
(`node:22.22.0-bookworm-slim@sha256:dd9d2197…87d94`, the multi-arch index resolved from Docker
Hub on 2026-09-22; its `linux/amd64` image carries `NODE_VERSION=22.22.0`), every
`node-version` in `.github/workflows/ci.yml` and `deploy.yml`, the pin stated in ADR 0003 and
the comments that repeat it (`.github/dependabot.yml`, `zone-a/`). `test/runtime.test.ts` now
pins ICU `77.1` as well as Unicode `16.0`, and pins the one word-segmentation behaviour that
moved (below). No code, version literal, vector or contract changed.

**Why.** Security: 22.14.0 was released on 2025-02-11, and 22.22.0 (2026-01-12) is the third
Node 22 security release after it. 22.22.0 is also the last Node 22 release on Unicode 16.0, established by running each release's own binary from
nodejs.org, not by reading notes: 22.22.0 reports ICU 77.1 / Unicode 16.0; 22.22.1, 22.22.2,
22.22.3, 22.23.0 and 22.23.2 all report ICU 78.2 / Unicode 17.0, which would be a new
`NORMALIZATION_VERSION`. The security fixes after 22.22.0 therefore cannot be taken without a
normalisation change; that is a separate, larger decision.

**Impact assessment (step 0).** The runtime is imported by everything; what matters is what
takes behaviour from ICU. Measured by running the same inputs through the release binaries of
22.14.0 and 22.22.0 (darwin-arm64, checksums verified against nodejs.org `SHASUMS256.txt`):

- NFC and NFD of every Unicode scalar value (U+0000 to U+10FFFF, surrogates excluded):
  identical. The `\p{L}\p{N}\p{M}` word-character class the verifier uses for word edges
  (`docs/fidelity-normalization.md` section 6): identical for every scalar value.
- `npm run check` under 22.22.0: green, including `contracts:check`, which regenerated the
  contract schemas, `test/fixtures/fidelity/vectors.json`, the contract fixtures and the
  differential smoke corpus with no drift. A seeded differential corpus of 3,000 cases for
  each of three seeds (20260920, 1, 42) is byte-identical between the two runtimes.
- **One behaviour moved.** `Intl.Segmenter` word segmentation, which the ingress gate uses to
  bound unverified free text to 20 words (`src/contracts/canonical-submission.ts`, ADR 0002),
  now keeps a colon between two letters inside one word: `a:b` (and the full-width and small
  colons U+FF1A, U+FE55) is one word under ICU 77.1 and was two under 76.1. With a digit on
  either side it still splits. Over every scalar value probed between letters, between digits
  and between spaces, these three are the only differences. The effect is a slightly looser
  word count for colon-joined tokens; the 300-character and aggregate bounds are unchanged.
  It moves no hash, no fidelity report and no approved content.
- Zone A's Python port uses `unicodedata` (Unicode 16.0.0 on Python 3.14) and no ICU; it is
  untouched and its differential agreement is unchanged, because the TypeScript side of the
  corpus is byte-identical.
- Previously produced evidence remains reproducible: nothing that enters a hash depends on
  segmentation. Step 7 does not apply.

**On the trigger.** ADR 0003's decision paragraph says a runtime whose "Unicode or ICU version
differs from the pinned one" is a new `NORMALIZATION_VERSION`, and defers to
`docs/fidelity-normalization.md` section 8 as the single normative statement; section 8 names
changes to sections 2–6 and says nothing of the runtime, and this README's procedure names a
Unicode drift. ICU moved and Unicode did not. `NORMALIZATION_VERSION` stays
`fidelity-norm/1.1.1` on the evidence above: no normalised text, report or vector changed. Decided 2026-09-23: section 8 governs, as ADR 0003 itself says, and nothing in sections 2–6
changed, so there is no new version. ADR 0003's sentence was amended the same day to match: a
runtime change is a controlled change that must be re-measured, and becomes a new version only
if an output in that scope changes. The word-limit change is outside the fidelity scope (it is
the gate's bound on unverified structured text) and is recorded here. Follow-up: the word
counter in `src/contracts/canonical-submission.ts` builds `Intl.Segmenter` with the runtime's
default locale; pinning an explicit locale would remove the last environment-dependent input to
the gate.

**Steps 1–6.** 1–3: no version literal, schema or vector changed. 4: `test/runtime.test.ts`
"runs on ICU 77.1" and "segments words as the pinned ICU does, colon between letters included",
both of which fail on 22.14.0 (run). 5: ADR 0003's pinned-runtime consequence names
`node:22.22.0`, ICU 77.1. 6: UR-35.

**Blast radius.** The deployed worker and query images change base; `test/runtime.test.ts` runs
on CI's Node, not inside the image, so the image's own `process.versions` is taken from the
same release by construction (the official image installs the nodejs.org tarball) rather than
observed; a Cloud Build step that prints it would close that. A developer on a Node other than
22.22.0 or another ICU 77.1 / Unicode 16.0 build now fails `test/runtime.test.ts`, as intended.

**Approval (step 8).** Not obtained: author and releaser are the same identity. The trigger
question above needs the system owner's decision before merge.
