# Recorded change: run manifest 3.0.0 and the persisted run's commit order, 2026-09-27

**What changed.** `RUN_MANIFEST_VERSION` moved from `2.0.0` to `3.0.0`, a major under ADR 0002.
A persist-mode manifest is now signed **before** the FHIR transaction, so it no longer says
`persisted`. Its status is `authorised`: validated, and authorised to write exactly the transaction
it names. `persistence.transactionResponseHash` is replaced by `persistence.transactionSha256`, the
SHA-256 (canonical JSON) of the exact transaction Bundle the worker sends, which is kept as the
run's `persist-transaction` evidence object. `completedAt` is when validation and the
transformation completed, so it falls before the transaction.

The two statuses are two shapes: a discriminated union on `status`, published as a JSON Schema
`oneOf`.

- A `validated` manifest has `dryRun: true` and no `persistence`.
- An `authorised` manifest has `dryRun: false` and `persistence`.
- The generated Zone A model enforces this too (`zone-a/tests/test_run_manifest_status.py`).

`RunStatus` loses `rejected` and `failed`, which no version ever wrote, and `persisted` moves to
the ledger row. 1.0.0, 1.1.0 and 2.0.0 stay readable through `AnyRunManifestSchema`, with 2.0.0
frozen as `RunManifestV2Schema`.

A persisted run now does these steps, in order:

1. It writes its evidence objects. Each write is conditional on the object not existing
   (`ifGenerationMatch: 0`), so the first write claims the runId.
2. It writes `persist-transaction`, then the signed manifest.
3. It runs the FHIR transaction. Entries are in dependency order: every entry comes after each
   entry it references.
4. It writes a hash-only `commit` object: the response's hash, the commit time and the Bundle
   version written.
5. It writes the ledger row. The row says `persisted`, its `completed_at` is the commit time, and
   it carries two new NULLABLE columns: `transaction_sha256` and `target_bundle_version_id`.
6. It publishes lineage, best effort.

Evidence writes and the ledger insert are retried within a bound: five retries over about two
minutes. The ledger insert carries the runId as `insertId`, so BigQuery can drop a duplicate left
by a retry.

The ledger insert gets a longer tail, about six minutes with at most a minute between attempts,
for one refusal only: "no such field". BigQuery's streaming path caches a table's schema for a
few minutes after a column is added. Every persisted run writes the two new columns, starting
with the deploy's smoke run minutes after the apply that adds them.

The residual risk: a cache slower than six minutes answers `committed-unrecorded` for a run that
did commit. The deploy's smoke request is also bounded at 480 s, which the tail can approach.

Before the transaction, any 412 on an evidence write fails closed as `run-id-reused`. That holds
even when the 412 answers a retry after an unanswered attempt, because the object may be another
run's under the same runId, and the worker (`objectCreator`) cannot read it to tell. Only the
post-commit `commit` object takes such a 412 as its own write. A rate-limited attempt (429) is
never counted as unanswered, because it wrote nothing.

In the transaction, the standalone resources carry `Type/id` references to the other entries
instead of `urn:uuid` placeholders. The document Bundle is written unchanged.

**What a missing ledger row means.** The ledger row records a committed run. A signed manifest
with no ledger row is one of two things:

- **A run that did not commit.** The transaction never ran, or the store refused it. The refusal
  is atomic, so nothing is live.
- **A run that committed but went unrecorded.** The transaction succeeded, and then the `commit`
  object or the ledger insert failed after its retries. The worker answers
  `committed-unrecorded` and logs the manifest hash.

The target store tells the two apart. Only the second case left a Bundle version, and that
version was written by the `persist-transaction` object's transaction, whose hash the manifest
signs.

**What the profile validators saw (not the stored form).** Both the official HL7 validator and
the Cloud Healthcare API `$validate` check the List and the Composition as the transform wrote
them, with `urn:uuid` references. The stored copies differ only in the form of those references.
`test/healthcare-transaction.test.ts` proves this: mapping each stored `Type/id` back to the
fullUrl of the entry it names gives back exactly the validated resource, and each stored
reference names an entry of the same transaction.

The stored forms are not sent to `$validate` for one reason. Once references are `Type/id`, the
FHIR store's referential integrity could check them against the store before the transaction
has written the targets. This project has never observed that behaviour, and it cannot be
verified without the cloud. Validating the stored forms directly is left for a change that can
be tested against the store.

**Why.** The audit of 2026-09-27 (batch B02) and its first review found these problems:

- The transaction committed before any evidence was written or signed.
- A persisted run started without a signing key or a ledger dataset.
- A replayed runId persisted another version and could never finish.
- Every persisted reference between resources was a literal `urn:uuid:` string that nothing
  resolved.
- A manifest signed before the transaction could not honestly say `persisted`.

**Impact assessment (step 0).** Importers of `src/contracts/run-manifest.ts`:

- the pipeline;
- the ledger row (`src/gcp/evidence.ts`), which now takes the commit;
- the contract generator;
- Zone A's generated model.

Previously produced evidence: 2.0.0 manifests and their ledger rows are unchanged and still
parse.

What is written to the FHIR store changes. After this change, a run writes the List, the
Composition and the product-graph resources with `Type/id` references, which the store's
referential integrity now checks and BigQuery's `resourceId` columns now carry.

The ledger table gains two NULLABLE columns, added in place. `infra/main.tf` must be applied
before a worker that writes them is deployed; `infra/run.tf` already orders the table before
the service. No fidelity vector, contract fixture or approved hash moves.

6. None.

**Blast radius.**

- A deployment with `DRY_RUN=false` does not start without `KMS_MANIFEST_KEY` (a key version)
  and `TRANSFORMATION_LEDGER_DATASET`.
- A reused runId answers 409 `run-id-reused`.
- A crosswalk refusal answers 422 `crosswalk-refused`.
- A committed run whose record could not be written answers 500 `committed-unrecorded`.
- The workflow requires its `source` argument, and it fails a run whose response names no
  persisted Bundle version.
